01 / Project

Event-Driven Order Platform

A hands-on AWS project focused on event-driven architecture, asynchronous messaging, reliability engineering, security, automation and observability.

From HTTP request to completed order

The API deliberately separates the synchronous client response from the asynchronous processing path. The client receives an HTTP 202 Accepted while the order continues through the event pipeline.

API Gateway validates and forwards order requests
Order API Lambda creates a PENDING order in DynamoDB
OrderCreated is published to EventBridge V2
EventBridge routes the event to SQS
Order Processor consumes asynchronously
Step Functions orchestrates workflow execution
Order Worker completes the business step
DynamoDB records the final COMPLETED state
AWS LambdaAPI GatewayDynamoDBEventBridge V2SQSStep Functions

03 / Reliability

Failure is part of the design.

The project deliberately exercised the failure path instead of only demonstrating the happy path.

FAILURE TEST

Processor failure → DLQ

A controlled customer ID triggered an intentional processor exception. The same SQS message was observed across receive counts 1 → 2 → 3, after which SQS moved it to the DLQ.

04 / Idempotency

Duplicate events are treated as a design problem.

Step Functions uses the ProcessedOrderEvents table to claim an event before processing. A conditional DynamoDB write prevents the same event from being processed twice.

ClaimEvent

Attempt to create the event record with attribute_not_exists(eventId).

DuplicateEvent

If the conditional write fails, the workflow recognizes an already-claimed event and avoids duplicate business processing.

CompleteEvent

After successful processing, the event record is marked completed, preserving the processing history.
