## API

### Create Order

```http
POST /orders
```

Example:

```json
{
  "customerId": "CUST-001",
  "items": [
    {
      "productId": "PROD-001",
      "quantity": 2
    }
  ]
}
```

Successful response:

```http
202 Accepted
```

```json
{
  "orderId": "ORD-12345",
  "status": "PENDING",
  "message": "Order accepted"
}
```

The client does not provide `orderId`, `status`, or `createdAt`; these are generated by the backend.

## Reliability and Failure Recovery

The project deliberately tested the failure path:

```text
Order Processor Lambda
        ↓
      Failure
        ↓
   SQS retry #1
        ↓
   SQS retry #2
        ↓
   SQS retry #3
        ↓
       DLQ
        ↓
CloudWatch Alarm
        ↓
Recovery / Replay
        ↓
Normal Processing
        ↓
COMPLETED
```

The controlled failure used `CUST-FAIL-TEST`. The failure hook was removed after testing and the clean application code was redeployed.

The recovered order successfully reached `COMPLETED`.

The DLQ alarm entered `ALARM` during testing and returned to `OK` after recovery and cleanup.

## Idempotency

Duplicate-event protection uses the `ProcessedOrderEvents` DynamoDB table.

```text
Event received
      ↓
Attempt to claim event
      ↓
Already processed?
   /           Yes          No
  ↓            ↓
Skip         Process
```

This protects business processing from duplicate delivery.

## Step Functions

The workflow is:

```text
ClaimEvent
    ↓
ProcessOrder
    ↓
CompleteOrder
    ↓
MarkEventCompleted
```

The Order Processor Lambda starts the state-machine execution and the Order Worker Lambda performs workflow processing.

## IAM and Security

Dedicated IAM roles are used for the Lambda workloads.

Permissions are scoped to the resources required by each component.

Broad permissions such as:

```text
sqs:*
dynamodb:*
events:*
```

were intentionally avoided.

GitHub Actions authenticates to AWS using OIDC rather than long-lived AWS access keys.

## GitHub OIDC

```text
GitHub Actions
      ↓
GitHub OIDC token
      ↓
AWS STS
      ↓
IAM Role
      ↓
Temporary AWS credentials
```

The trust policy restricts access to the intended repository and main branch.

## Engineering Lessons Learned

### 1. Asynchronous processing changes API design

The API acknowledges the request rather than waiting for downstream processing.

### 2. SQS retry behavior must be tested

It is not enough to configure a DLQ. The project deliberately forced a processor failure and verified actual retry behavior.

### 3. DLQs provide failure isolation

A DLQ provides a place to isolate, inspect, and recover repeatedly failing messages.

### 4. Idempotency is essential

At-least-once delivery means consumers must tolerate duplicate events.

### 5. Least privilege should be designed per workload

Each Lambda receives only the permissions required for its responsibilities.

### 6. CI/CD should use temporary credentials

GitHub OIDC avoids storing long-lived AWS access keys.

### 7. Infrastructure and application deployment can be separated

Terraform manages infrastructure while GitHub Actions manages application-code deployment.

### 8. Failure testing is more valuable than only testing success

The project demonstrated:

```text
Failure
  ↓
Retry
  ↓
DLQ
  ↓
Alarm
  ↓
Recovery
  ↓
Successful processing
```
